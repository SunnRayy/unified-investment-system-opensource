# Supported Python: 3.9-3.13, tested on 3.9.6 and 3.13.7.
#
# Pinned to the exact versions this project's test suite and app are
# validated against. Program OSR WS-7 finding, 2026-08-17: a fresh
# `pip install -r requirements.txt` under an unpinned resolver picked newer
# numpy/scipy on a newer Python and changed at least one numeric function's
# behavior (test_sharpe_ratio returned None instead of a float). Unpinned
# installs are how "works on my machine" gets baked into a public repo —
# treat any version bump here as a deliberate, tested upgrade, the same
# discipline the fastapi/starlette pins below already established.
#
# numpy/scipy need a Python-version split, not a single hard pin: 2026-08-17
# regression (caught by the owner running quickstart by hand) — numpy==2.0.2
# has no Python 3.13 wheel, so pip falls back to a source build that needs a
# Fortran compiler most machines don't have, and a newcomer on any current
# Python (3.13 is `python3` on a stock macOS install) hit a 50+ line meson
# traceback on the very first command. Environment markers over a hard
# 3.9-3.12 range deliberately: a contributor shouldn't need to install an
# old Python just to try the project. Both branches are still exact pins
# (cp313 wheels confirmed via `pip install --dry-run` before landing), so
# reproducibility holds within each Python version, just not across the 3.13
# boundary — numpy/scipy don't guarantee identical numerics across major
# versions regardless of what this file pins.
numpy==2.0.2; python_version < "3.13"
numpy==2.5.2; python_version >= "3.13"
